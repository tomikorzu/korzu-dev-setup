# CMS template (Strapi)

Scaffolded standalone by `create-korzu-app --cms`, or as `apps/cms` when combined with other
layers. A hand-maintained, version-pinned Strapi project — not generated by `create-strapi-app`
at scaffold time. See "Why version-pinned" below before touching dependency versions.

## Core rules

- **Every dependency here is pinned to an exact version**, not a range — deliberately, unlike
  every other template in this repo. Strapi's admin panel, plugins, and core must all agree on
  compatible versions; a `^`-ranged `package.json` scaffolded today and installed months later
  can silently pull an incompatible combination. See "Why version-pinned" below.
- **Content types are defined by their schema, not by hand-editing generated files.** Add or
  change a collection/single type via `schema.json` + matching
  `controllers/`/`routes/`/`services/` files (the `article` content type is the pattern to copy).
  See the `strapi-content-types` skill.
- **Secrets are never committed.** `.env.example` ships with every secret key blank — generate
  real values per-project (see "Local development" below) and never reuse them across projects.
  See the `strapi-env-config` skill.
- **Biome** for lint/format — no ESLint/Prettier.
- **No automated test suite** — Strapi's own testing story (mocking its runtime/DB layer) is
  heavy for what a starting template needs. If this project grows real business logic beyond
  generated CRUD, add integration tests against a real test database rather than mocking Strapi.

## Why version-pinned

Every other template in this repo uses `^`-ranged dependencies, refreshed by normal `pnpm
update` hygiene. Strapi is the deliberate exception: its admin panel, core, and official plugins
(`@strapi/plugin-users-permissions`, `@strapi/plugin-cloud`) must all be on a mutually compatible
version, and Strapi doesn't manage that compatibility via semver ranges — it expects a
"generated once, upgraded deliberately" project, not a continuously-`^`-updated one. The
trade-off: this template needs a manual version bump (checked against Strapi's own migration
guide) when you want to move to a newer Strapi release — it will not drift forward on its own.

## Local development

```bash
docker compose up -d        # local Postgres
cp .env.example .env
# generate each secret and paste it into .env — see the comment in .env.example
node -e "console.log(require('crypto').randomBytes(16).toString('base64'))"
pnpm install
pnpm dev                    # http://localhost:1337/admin — create your first admin user
```

## Frontend integration

The Frontend template's `createStrapiClient()`
(`src/modules/shared/utils/strapi.util.ts`) already speaks this CMS's REST API — point its
`NEXT_PUBLIC_STRAPI_URL` at this app's URL (`http://localhost:1337` in local dev) and, for
protected content, generate an API token in the admin (Settings → API Tokens) for
`STRAPI_API_TOKEN`. No new Frontend code is needed to consume a new content type — just call
`getCollection`/`getEntry`/`getBySlug` with its plural API name (e.g. `"articles"`).

## Adding a new content type

Mirror `src/api/article/`: a `content-types/<name>/schema.json` describing the attributes, and
`controllers/`, `routes/`, `services/` files that each just re-export Strapi's core factory
(`factories.createCoreController` etc.) unless you need custom behavior — don't hand-write CRUD
that Strapi already generates for you.
